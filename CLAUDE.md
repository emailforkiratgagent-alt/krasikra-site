# krasikra-site — инструкция для Claude

Продающий сайт сети магазинов икры и рыбных деликатесов «Хозяин Камчатки» (Красноярск, 10 магазинов), домен krasikra.ru. Стратегическая цель — выход на страновой уровень (авиадоставка, доставка до двери в крупных городах), поэтому решения не должны быть завязаны на один город.

## Начни с этого

1. `docs/decisions.md` — принятые решения, открытые вопросы, статус. Читай перед любой работой.
2. `docs/xlabel/requirements.md` — требования к API X.Label, сценарии выбора магазина, оплаты и доставки.
3. `docs/xlabel/openapi-1.30.yaml` и `docs/xlabel/mobile-api-readme.md` — спецификация Mobile API 1.30.
4. `docs/xlabel/answer-2026-10-29.md` — что X.Label доработал для сайта (platform=web, адреса возврата, ключ сайта, одноразовый id_token).
5. `docs/brand/brand-web-guide.md` — фирменный стиль для веба. Логотипы: `public/brand/`.
6. `docs/infra/test-stand.md` — тестовый стенд в Yandex Cloud и выкатка.

## Архитектура

- **Next.js (App Router) + Payload CMS 3 + PostgreSQL**, TypeScript. Сайт и админка (`/admin`) — одно приложение, один Docker-контейнер (Yandex Cloud Serverless Containers, порт из `PORT`, по умолчанию 8080).
- **X.Label — источник правды** для каталога, цен, наличия, магазинов, доставки, заказов, оплаты, бонусов. Сайт ничего из этого не хранит как главную копию.
- **CMS только обогащает**: SEO, slug, доп. фото, состав/КБЖУ/хранение, описания для сайта, страницы, блог, баннеры, редиректы, отзывы.
- **BFF**: браузер ходит только к серверу сайта. Токен приложения X.Label, токены покупателей и `id_token` входа хранятся на сервере и никогда не отдаются в браузер.
- **Настройки интеграции X.Label** (адрес API, токен сайта `webAppToken`, публичный ключ) — в админке, глобал «Интеграция X.Label», доступ только роли `admin`. Токен шифруется в БД ключом из переменной окружения, в UI показывается замаскированным. Не храни секреты в коде и в репозитории.
- **Слой доступа к контенту**: страницы вызывают свои функции (`getProductContent`, `getPage`, …), а не Payload напрямую — чтобы CMS можно было заменить.

## Правила работы с X.Label (критично — иначе заказ не создастся)

- Базовый URL `https://<host>/api/v1.30/…`, заголовки `X-APP-TOKEN: Bearer <webAppToken>` и для методов пользователя `Authorization: Bearer <access_token>`. `platform=web` в `/settings`, `/versions`, `payments/init`; `version=1.0.0` в `/versions`.
- Ответ успеха — `{"response": …}`, ошибки — `{"error": "…"}`, **иногда со статусом 200** (`POST /orders`, `POST /people/addresses/new`): всегда проверяй поле `error`.
- Деньги — строки `"199.00"`, количество до 3 знаков, кратно `multiple_of`.
- **Цены**: `GET /products?store=` → цена магазина в `price` товара (акционная уже в `price`, прежняя в `old_price`). Без `store` цен нет. Сумма позиции = `round(кол-во × цена)` до копеек, половина вверх. X.Label сверяет каждую цену и все суммы до копейки. Перед `POST /orders` перечитывай цены магазина; при расхождении показывай покупателю «было → стало».
- **Доставка**: итог для адреса — `GET /shipment_methods/{id}/calc` (нужны авторизация и адрес с координатами). `-1.00` = расчёт пока недоступен, повторить через несколько секунд; отказ в доставке — поле `error` со статусом 200. При `by_request` (Яндекс Go) перед заказом вызывать `calc` заново, если истёк `valid_until`. `subtotal >= free_order_amount` → `shipment_price = "0.00"`.
- **Оплата**: `POST /orders/{id}/payments/init` (`platform=web`, `page_view=desktop|mobile`) → `formUrl` → возврат на `/order/{id}/success|fail` → `POST /orders/{id}/payments` с `payment_id = orderId` Сбера. Параметрам в адресе возврата не доверяй. Callback Сбера нет — фоновая проверка неоплаченных заказов на стороне сайта (до 30 мин).
- **Вход**: `/token/{telegram|whatsapp|max}/start` → ссылка (на десктопе — QR) → опрос `/token/{provider}` 2 с → 5 с, не дольше `expires_in`. 401 «Номер телефона не подтвержден» — ждать; «Истек срок действия токена» / «Вы не авторизованы» — остановить. `id_token` одноразовый.
- **`hash_code`**: UUID v4 браузера (долгоживущая httpOnly-cookie), шифрование на сервере ключом сайта RSA-OAEP SHA-256 / MGF1 SHA-256, base64. Обязателен в методах входа и в `/versions` с авторизацией.
- **Токены**: `refresh_token` одноразовый и бессрочный — обновлять только по 401 «Access token has expired.», строго последовательно на покупателя, новую пару сохранять сразу.
- **`/versions`** опрашивать без `Authorization` (иначе пишется «вход» в статистику).
- Купоны и бонусы в онлайн-заказах не используются. Гостевых заказов нет. Отмены заказа покупателем нет.

## Фирменный стиль (кратко)

Тёмно-синий `#14324C`, икорный `#DC3C28` (мелкий текст на белом — `#C2321F`), светло-бежевый `#E7DBC8`, светло-серый `#BCBEBF`. Шрифт — DIN Pro (лицензия под вопросом, иначе согласованная замена). Надпись логотипа — только SVG. Линейная фирменная графика (вулканы, маяк, сейнер, краб, волны). Характер: брутальный, надёжный, профессиональный — строгая вёрстка без пестроты.

## Правила для кода

- Язык интерфейса — русский; код, имена переменных и коммиты — на английском, комментарии по делу.
- Деньги считать в копейках (целые числа), в строки `"199.00"` переводить только на границе с API.
- Все вызовы X.Label — через один клиент (`src/lib/xlabel/`), с типами из OpenAPI и обработкой `{"error"}` при 200.
- Персональные данные — только на серверах в РФ (Yandex Cloud).
- Тестовый сайт закрыт от индексации (`X-Robots-Tag: noindex`).
- Работать в ветках, в `main` — через pull request (см. «Порядок работы с PR»).

## Порядок работы с PR (согласован с владельцем проекта 31.10.2026)

Владелец проекта — не программист и проверяет результат, а не код.

1. Любые изменения кода — в отдельной ветке и через pull request. Документы (`docs/`, `CLAUDE.md`) можно коммитить прямо в `main`.
2. Описание PR пишется по-русски, человеческим языком, с разделами:
   - **Что изменилось** — для покупателя / администратора, без жаргона;
   - **Как проверить** — пошагово: какую страницу открыть, что нажать, что должно получиться;
   - **Риски** — что может пойти не так и что уже проверено;
   - **Скриншоты** — десктоп и мобильная версия для изменений интерфейса.
3. Автопроверки (сборка, линтер, тесты) должны быть зелёными. С красными PR владельцу не отправляется.
4. Для PR, затрагивающих оплату, вход и токены, расчёт цен и доставки, настройки интеграции — дополнительно независимое ревью отдельным агентом; итог ревью кратко в PR и в чате.
5. В чат владельцу: ссылка на PR и кратко, что проверить.
6. **Вливать PR в `main` только после явного одобрения владельца в чате.** Точная фраза не нужна — подходит любое сообщение, по смыслу одобряющее именно этот PR: «принято», «ок, вливай», «PR №3 проверил, всё хорошо», «можно в main». Правила:
   - одобрение должно относиться к конкретному PR: если открыто несколько, а из сообщения непонятно какой — уточнить;
   - «ок» в ответ на другой вопрос или просто «понял» — не одобрение;
   - одобрение с замечаниями («принято, но поправь цвет кнопки») — сначала поправить, показать, влить;
   - если есть сомнение — спросить «вливаю PR №N?», а не вливать.
   Без одобрения — не вливать, даже если всё зелёное.
7. После вливания — выкатить `main` на тестовый стенд (`docs/infra/test-stand.md`) и сообщить в чат, что изменения на стенде.
